## 1. 🔴 확실한 버그

### 1-1. `marketCap` 이 **여전히 거꾸로다** — 「방향을 뒤집었다」는 수정이 코드에 도달하지 않았다

**파일:줄** — `signalLight.ts:1973-1979` (`grade`) · `1813` (`DESCENDING`) · `1369-1371` (설정) · `2623-2653` (계산)

문제의 근원은 `grade()` 다.

```ts
function grade(value: number, c: CheckConfig): number {
  const hi = Math.max(c.threshold, c.strongAt);
  const lo = Math.min(c.threshold, c.strongAt);
  if (value >= hi) return 100;
  if (value >= lo) return 50;
  return 0;
}
```

`hi`/`lo` 를 **크기로 정렬**하므로 `threshold > strongAt` 로 넣어도 방향이 안 뒤집힌다. **`grade()` 는 언제나 「클수록 좋다」다.**

2026-09-01 의 수정은 두 가지였다 — ① 자리를 맞바꿔 저장(`threshold: 5000, strongAt: 3000`), ② `saveConfig` 가 그 자리를 다시 안 바꾸도록 `DESCENDING` 예외(`signalLight.ts:1837-1838`). **둘 다 `grade()` 를 건드리지 않았다.** `DESCENDING` 은 `saveConfig` 안에서만 쓰이고 채점에는 관여하지 않는다(`1813` 정의, `1838` 유일한 사용처).

실제 채점 결과 (저장된 설정 `th5000 / sa3000` 그대로 계산):

| 시총 | marketCap 점수 | 의도한 점수 |
|---|---|---|
| 1,000억 | **0** | 100 |
| 2,000억 | **0** | 100 |
| 3,000억 | 50 | 100 |
| 5,000억 | **100** | 0 |
| 20조 | **100** | 0 |

표본 27,970관측 분포 — **79.6% 가 100점, 13.4%(3천억 미만)가 0점**이다.
즉 「강세·약세 양쪽에서 승률 +8.1 / +7.6%p」라고 문서에 적힌 **3천억 이하 소형주 집단이 무게 3짜리 기준에서 0점을 받고 있다.** hint(`1371`)는 "클수록 감점"이라고 적혀 있고 코드는 정확히 그 반대를 한다.

**고치면 무엇이 바뀌나** — `value` 축이 통째로 뒤집힌다. 강세장에서 `value` 축은 `marketCap`(3) + `largeCap`(2) 둘뿐이라(아래 4번 표 참고) **실적 축 점수 = 시가총액 점수**다. 지금 20조 종목이 `value = (100×3 + 50×2)/5 = 80`, 2천억 종목이 `0` 을 받는다. 방향을 고치면 정확히 뒤집힌다. 문서가 말하는 「꼭대기를 되살렸다(-2.33 → +8.83%p)」는 효과는 **아직 한 번도 실전에 적용된 적이 없다.**

**시뮬레이터도 같은 `grade()` 를 쓴다**(`signalSamples.ts:322-328`, `414-421`). 그래서 시뮬레이터 화면의 숫자도 같은 방향으로 틀려 있고, 「고쳤더니 좋아졌다」는 측정은 실제로는 **문턱 구간이 3천억~1조에서 3천억~5천억으로 좁아진 효과**를 본 것이다(둘 다 「클수록 좋다」인 채로).

고치려면 `grade()` 에 방향 인자를 넣거나(`DESCENDING.has(c.key)` 를 참조), `marketCap` 을 「음수 시총」처럼 단조 증가 값으로 변환해야 한다.

**고치면** — 켜기 전에 반드시 배선을 넣어야 한다. 혹은 지금처럼 못 재는 동안은 `CheckKey` 에서 빼거나 「배선 없음」을 코드가 알게 해야 한다.

### 1-3. 시뮬레이터는 **탈락(veto)을 전혀 적용하지 않는다** — 「초록」 집합이 실전과 다르다

**파일:줄** — `signalSamples.ts:514-574` (`scoreFeat`) · `signalSimulate.ts:332, 915, 1268`

`scoreFeat` 어디에도 `veto`/`vetoAt` 를 읽는 곳이 없다. `grep veto server/src/signalSimulate.ts` 도 0건이다. 실전은 `signalLight.ts:3003-3011` 에서 **탈락 하나면 무조건 빨강**이다.

표본으로 재면:

|---|---|
| `flowRatio` raw ≤ -0.5 (탈락) | **33.7%** |
| `overhead` ≥ 60 (탈락) | **33.7%** |

### 1-4. 시뮬레이터가 **약세장 관측을 100% 버린다** — 표본의 53%가 채점 밖이다

**파일:줄** — `samplesFromLedger.ts:352-356` · `signalSamples.ts:444` · `signalSimulate.ts:334-337`

`samplesFromLedger.ts` 가 네 칸을 **상수 null 로 박아 둔다:**

```ts
profitYoY: null,
qStreak: null,
qYoY: null,
qMargin: null,
```

표본 파일 확인 — `profitYoY` · `qStreak` · `qYoY` · `qMargin` 모두 **비어 있지 않은 값 0.0%**(27,970건 전부 null).

그런데 `profitGrowth` 는 `enabled: true, weight: 2, regime: "bear"` 다. 약세장에서 켜지는 기준의 무게 합은

`flowPersist 2 + flowAccel 1 + smartMoney 1 + flowRatio 2 + profitGrowth 2 + marketCap 3 + overhead 2 + shortSaleUp 1 = 14`

이고 `profitGrowth` 는 언제나 null 이므로 커버리지 상한이 **12/14 = 0.857** 이다. `minCoverage = 0.9` 이므로 **모든 약세장 관측이 예외 없이 탈락**한다.

실측 (저장된 설정 그대로 재현):

```
장세 판정된 날:  강세 30일 / 약세 50일
강세 관측 13,202  커버리지 미달 5,193  초록 857
약세 관측 14,768  커버리지 미달 14,768  초록 0     ← 전부
커버리지 히스토그램: bear:0.857 → 14,310건 / bear:0.786 → 458건
```

**결과** — 지금 시뮬레이터가 내는 모든 통계는 **강세장 30일치 관측만으로 낸 값**이다. 그리고 그 시뮬레이터로 검증하겠다던 `profitGrowth`(약세 전용)와 `flowRatio`(약세 전용) 두 기준은 **원리적으로 한 번도 채점된 적이 없다.** `signalSamples.ts:131-154` 의 긴 주석(「그날 알 수 있었던 영업이익 증가율 … look-ahead 를 어떻게 막나」)은 지금 구현과 맞지 않는다 — 그 계산은 옛 `signalBacktest` 경로에만 있고 원장 경로(`samplesFromLedger`)에는 없다.

### 1-5. 약세장에서는 **추세 축이 통째로 사라진다** — 축 가중치 1.5 가 조용히 증발한다

**파일:줄** — 설정 `signalConfig.json` · 축 평균 `signalLight.ts:2889-2923`

추세 축에서 켜진 기준은 `newHigh`(regime **bull**)와 `etfBacking`(regime **bull**) 둘뿐이다. 나머지 추세 기준(`trend`·`nearHigh`·`pullback`·`sectorStrength`·`naverTheme`·`themeStrength`·`myThemeStrength`)은 전부 꺼져 있다.

따라서 **약세장에서는 추세 축에 평가되는 기준이 0개**다. `2890-2892` 에서 `total === 0` → `score: null, level: "unknown"` 이 되고, `2913` 의 `scored` 에서 빠지고, `2914` 의 `wSum` 에서도 빠진다.

종합 점수의 정의가 장세에 따라 조용히 바뀐다:

```
강세장:  (추세×1.5 + 수급×1.0 + 실적×0.6) / 3.1
약세장:  (          수급×1.0 + 실적×0.6) / 1.6     ← 추세 축 없음
```

가장 무거운 축(1.5)이 사라지는데도 점수는 같은 0~100 눈금에 올라간다. 그리고 전종목 기준으로 재면 **80일 중 63일이 약세장**이다(아래 2-5 참고) — 즉 **다섯 날 중 네 날은 추세를 하나도 안 보고 신호등을 낸다.**

화면의 추세 축은 그날 「-」로 뜬다. 사람이 「추세를 못 쟀나 보다」로 읽기 쉬운데 실제로는 「추세를 볼 기준이 하나도 없다」다.

## 2. 🟠 실전 · 시뮬레이터 불일치

| 규칙 | 시뮬레이터 | 실전 | 판정에 미치는 영향 |
|---|---|---|---|
| **탈락(veto)** | 없음 | `raw` 로 판정, 걸리면 무조건 빨강 (`3003-3011`) | 표본의 **53.7%** 가 실전에서 탈락. 시뮬 초록 857 중 **66건(7.7%)** 이 실전 빨강 |

## 3. 🟡 의심 — 확인 필요

### 3-1. `shortSaleUp` 의 hint 가 코드와 다른 것을 말한다
`signalLight.ts:1619` — `hint: "최근 5일 평균 공매도 거래비중(%)"`.
실제로 채점하는 값은 `diff + level` = (최근 5일 평균 − 이전 15일 평균, **%p**) + `max(0,(recent-20)/20)` (`2836-2839`). 문턱 0 / 만점 5 도 그 %p 눈금에 맞춘 값이다(`1610-1618` 주석이 그렇게 설명한다). **hint 만 옛 정의로 남았다.** 설정 화면에서 사람이 「비중 %」로 알고 문턱을 만지면 엉뚱한 값이 된다. 표본 등급 분포는 0점 8,320 / 50점 10,815 / 100점 780.

### 3-2. `overhead` 의 탈락선(60)이 「심각」선(65)보다 **낮다**
`signalLight.ts:1504-1517` — `threshold 40 · strongAt 65 · vetoAt 60`.
`CheckConfig.veto` 주석(`147-148`)은 "이 기준이 「심각」이면"이라고 적는데, 실제로는 **등급 50(위험 시작)에 불과한 종목도 탈락**한다. 표본에서 33.7%가 여기 걸린다 — 탈락 치고는 매우 넓다. 의도한 것인지 확인이 필요하다.

### 3-3. `profitGrowth` 가 적자 기업에서 방향을 잃는다
`signalLight.ts:2618` — `((latest - prev) / Math.abs(prev)) * 100`.
`prev = -100억`, `latest = -50억` 이면 **+50%** 가 나와 만점 근처를 받는다. 여전히 적자인데 「영업이익이 늘었다」로 읽힌다. 반대로 `prev = +10억`, `latest = +30억` 은 +200%. 부호가 바뀌는 구간에서 이 지표는 크기 비교가 안 된다. 문서가 말하는 「반토막(-50%↓)이 제일 좋다」는 이상한 결과에 이 계산이 기여했을 가능성이 있다 — **추측이다.**

### 3-4. `pullback` 의 「연속 환산」이 `grade()` 3칸에서 무너진다
`signalLight.ts:2371-2372` — `near = 1 - |pct-90|/5`, `g = G(50 + near*50)` (범위 50~100), 설정은 `threshold 50 / strongAt 100`.
`grade()` 는 `>= 100` → 100, `>= 50` → 50 이므로 **정확히 pct=90.0 일 때만 100점**이고 나머지 눌림목은 전부 50점이다. 주석(`2351-2354`)이 말하는 "89.9% 와 95.1% 가 하늘과 땅 차이가 되는 것을 막는다"는 목적이 달성되지 않았다. 지금은 꺼져 있다.

### 3-5. 거래대금 하한이 **다른 기준의 켬/끔에 의존한다**
`signalLight.ts:2111` — `wantInfo = need.has("marketCap") || need.has("volume") || need.has("flowRatio")`.
`tradeEok`(`2262-2271`)는 `info` 응답에서 나오고, 없으면 `chartRows[0].trde_prica`(= `wantChart` 필요)로 물러선다. 셋 다 끄고 `wantChart` 도 없으면 `tradeEok = 0` → `tooThin = false`(`2974`) → **`minTradeValue` 문턱이 조용히 사라진다.** 지금 기본 설정은 `marketCap` 이 켜져 있어 드러나지 않는다. 「판정 전체가 쓰는 값」이라고 주석(`2252-2256`)에 적어 두고 실제로는 검사 하나에 매달려 있다.

### 3-6. `flowPersist` 는 못 잰 구간을 **감점으로 처리**한다
`signalLight.ts:2455-2457` — 4구간만 재도 판정하고, `pos`(플러스 구간 수)를 **절대값으로** `threshold 2 / strongAt 5` 와 비교한다.
4구간만 잰 종목은 `pos` 최대가 4 이므로 **만점(5)을 구조적으로 못 받는다.** 「모르는 것을 0 으로 만들지 않는다」는 이 파일의 원칙과 어긋난다 — 분모를 안 맞추면 덜 잰 쪽이 자동으로 낮은 점수를 받는다. (`value` 문자열은 `${pos}/${measured.length}구간` 으로 분모를 보여 주지만 채점은 분모를 안 쓴다.)

### 3-7. `flowAccel` 전환 케이스가 가짜 `raw` 를 남긴다
`signalLight.ts:2481-2483` — 20일 순매도 + 5일 순매수면 `g = G(c.strongAt)` → `raw = 2.5`(= strongAt).
「전환」이라는 사건에 배수 2.5 라는 **측정하지 않은 숫자**가 붙는다. 조건 검색이 `raw` 를 비교값으로 쓴다고 `2286-2293` 이 명시하므로, 「가속 ≥ 2.4배」 조건이 실제로는 순매도 전환 종목까지 잡는다.

### 3-8. `mergeConfig` 가 `flowDays`·`greenAt`·`riskRedAt` 을 검증 없이 통과시킨다
`signalLight.ts:1670-1672` — `{...DEFAULT_CONFIG, ...saved, ...}`.
`minCoverage`·`greenTo`·`minTradeValue`·`bullAt`·`maLines` 는 아래에서 범위 검사를 다시 하지만 `greenAt`·`yellowAt`·`flowDays`·`riskYellowAt`·`riskRedAt`·`axisWeights` 는 저장본 값이 그대로 이긴다. `flowDays` 타입은 `5|10|20` 인데 런타임 강제가 없다.
참고: 현재 저장 파일에 `minTradeValue` 키가 **아예 없다** — 검증부(`1748-1753`)가 기본 100 으로 되돌리므로 동작에는 문제가 없다.

### 3-9. 커버리지·차단 플래그의 우선순위 때문에 화면이 이유를 잘못 말한다
`signalLight.ts:2959 → 2975 → 2982 → 2987`.
`lowCoverage` 가 먼저 green→yellow 로 내리면 그 뒤의 `overHeated`·`riskCapped` 는 `level === "green"` 조건에 걸려 **false 로 기록된다.** 판정 색은 맞지만 「왜 초록이 아닌가」의 이유 목록이 하나만 남는다. 여러 이유가 겹친 종목에서 사람이 잘못된 결론을 낸다.
