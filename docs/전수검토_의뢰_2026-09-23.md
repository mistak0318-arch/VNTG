### 2. 이번 회차의 범위

**한 갈래만 맡는다.** 벤티지가 지정한 갈래는 다음 중 하나다:

- **(가) 값의 일관성** — 같은 개념이 여러 화면·출처에서 같은 수를 말하는가
- **(나) 조용한 실패** — 실패가 성공으로 기록되거나, 빈 결과가 정상으로 보이는 자리
- **(다) 손질의 순서** — 한 값에 여러 보정이 겹칠 때 서로를 무효로 만드는 자리
- **(라) 화면의 상태** — 탭·종목·기간을 바꿔도 옛 값이 남는 자리
- **(마) 바깥 의존** — 외부 API 가 규약을 바꿨을 때 조용히 빈 화면이 되는 자리

범위를 넘어가는 발견은 **「범위 밖」으로 한 줄만** 적고 파고들지 마라.

### 3. 어떻게 찾는가 — 갈래별 구체적 방법

#### (가) 값의 일관성

한 종목·한 순간을 골라 **여러 화면이 말하는 같은 값**을 맞댄다. 실제로 어긋났던 예:

- 종목 상세의 큰 숫자(통합)와 그 옆 당일 봉(KRX) — 시가가 1,146,000 대 1,189,000 이었다
- 야간선물 시트의 큰 숫자 `1,129.9 +1.37%` 와 바로 위 카드 `종가 1,128.00 −0.79%`
  — **같은 순간의 현재가가 갈리고 부호까지 반대**. 두 출처가 다른 「전일」을 쓴다
- 거래대금이 백만원인지 억원인지 (`ka10032` 는 백만원)

찾는 법: `grep` 으로 같은 개념이 계산되는 자리를 모두 찾아 **기준값(base)이 무엇인지** 적는다.
기준이 둘 이상이면 그 자체가 항목이다.

#### (나) 조용한 실패

- `catch` 가 **빈 배열·null 로 갈음**하는 자리를 전부 찾아라: `.catch(() => [])`,
  `.catch(() => null)`, `catch {}`. 각각에 대해 **그 실패가 화면에서 어떻게 보이는지** 적어라.
  「빈 목록」과 「못 받았다」가 구분되지 않으면 항목이다.
- **성공/실패 기록이 결과물과 어긋나는 자리.** 실제 예: 뉴스 4탭이 HTTP 200 에 0건인데
  `recordApiCall(..., "ok")` 로 적혀, 계기판은 `ok 1507 · failed 0` 인데 화면은 한 달간 비었다.
- 점검: `server/data/apiUsage.json` 의 성공 수와 그 기능의 **실제 산출물 수**를 견줘라.

#### (다) 손질의 순서

한 값이 여러 번 덮이는 자리를 **시간 순서로** 적어라. 실제 예(2026-09-23):

```
① 등락률이 0 이면 어제 값으로 메운다
② 「거래대금 0 이면서 등락률 0」인 줄이 8할이면 어제 표 전체를 되살린다
   → ①이 먼저 돌아 ②가 영영 안 걸린다. 게다가 else 로 빠져 원본 파일을 0짜리로 덮어썼다
```

찾는 법: `rankSpec.ts` 처럼 한 응답을 여러 단계로 손질하는 파일에서, **판정이 보는 값이
그 판정 전에 이미 바뀌었는지**를 따져라. 「판정 함수는 옳은데 부르는 시점이 틀린」 것이 이 유형이다.

#### (라) 화면의 상태

- `innerHTML`·`ref` 로 **명령형으로 그리는 자리**는 데이터가 바뀔 때 다시 그리는지 확인하라.
  실제 예: 차트 띠가 `if (!bar.innerHTML)` 조건 탓에 탭을 옮겨도 옛 값을 들고 있었다.
- `useEffect` 의 deps 에 **바뀌는데 안 들어간 값**이 있는지.
- 이 앱의 탭은 **언마운트하지 않고 `display:none`** 이다(`App.tsx`). 숨은 화면이 계속 도는
  `setInterval` 이 아직 ~70곳 남아 있다(`docs/다음작업_TODO.md` 의 표). 목록의 정확성을 검증하라.

#### (마) 바깥 의존

- 외부에서 긁는 모든 URL을 **실제로 한 번씩 호출해** 살아 있는지 확인하라(네이버·야후·DART 등).
  키움·한투는 **조회 한도가 있으니 부르지 마라** — 코드만 보라.
- HTML 을 정규식으로 파싱하는 자리는 **셀렉터가 아직 맞는지** 실측하라.
  실제 예: 네이버가 PC 금융뉴스를 걷어내 302 로 보내면서 파서가 0건을 뱉고 있었다.
- 이미 만들어 둔 점검 도구를 쓰고, 없으면 같은 꼴로 만들자고 제안하라:
  `server/tools/newsCheck.ts` · `cfEdge.ts` · `corsCheck.ts` · `recentCheck.ts`
  (모두 서버를 안 띄우고 돌며 키움을 안 쓴다)

### 4. 산출물 형식

`docs/전수검토_<갈래>_2026-09-23.md` 파일 하나로 남겨라. 항목마다 **다음 일곱 칸을 다 채워라.**
못 채우는 칸이 있으면 그 항목은 **아직 항목이 아니다** — 「미확인」 절에 따로 모아라.

| 칸 | 내용 |
|---|---|
| 증상 | 사용자가 보는 현상 한 줄 |
| 자리 | `파일:줄` |
| 근거 | **아래 등급 중 하나를 반드시 붙인다** |
| 재현 | 붙여 넣으면 도는 명령 또는 클릭 순서 |
| 영향 | 돈·판단에 닿나 / 보기만 불편한가 |
| 왜 안 잡혔나 | 지금 장치(로그·계기판·타입)가 왜 못 잡았나 |
| 제안 | 고치는 방향 **한 줄**. 코드는 쓰지 마라 |

**근거 등급** — 이게 이 의뢰의 핵심이다:

- **실측** — 내가 직접 돌려 본 결과. 명령과 출력을 그대로 붙인다
- **코드근거** — 코드를 읽어 논리적으로 확실. 인용한 줄을 붙인다
- **짐작** — 그럴듯하지만 확인 못 함. **반드시 「짐작」이라고 쓴다**

짐작이 나쁜 게 아니다. **짐작을 실측처럼 적는 것**이 나쁘다.

### 5. 우선순위

「많이 찾기」가 목표가 아니다. **돈과 판단에 닿는 것부터**:

1. 주문·계좌·체결에 닿는 값 (틀리면 돈이 샌다)
2. 매매 판단에 쓰는 수 (등락률·거래대금·수급·신호등 — 틀리면 잘못 산다)
3. 조용히 비는 화면 (있는 줄 알았는데 없던 것 — 오늘 실제로 한 달간 있었다)
4. 보기 불편한 것

항목 20개짜리 목록보다 **1·2번에서 근거가 단단한 5개**가 낫다.

### 6. 재발 방지 — 이게 진짜 요청이다

벤티지의 말: *"계속해서 고쳐나갈 수도 없는 거야. 한번 만들어지면 계속 써야 되는데."*

그러니 항목마다 「고치자」로 끝내지 말고, **같은 종류가 다시 나면 스스로 드러나게 할 방법**을
같이 적어라. 우선순위는 이렇다:

1. **조용한 실패를 시끄럽게** — 빈 결과를 `ok` 로 적지 않기, 화면에 사유 적기
2. **상시 점검 도구** — `server/tools/*.ts` 꼴로. 서버를 안 띄우고 키움을 안 쓰며, 한 번 돌리면
   「지금 멀쩡한가」가 30초에 나오는 것
3. 코드 수정

마지막에 **「지금 이 저장소에 없는 안전장치」** 절을 따로 두고, 가장 값싼 것부터 세 개만 꼽아라.

정확히 그렇게 났다(내가 9/22 에 넣은 보정이 내가 기대던 보정을 껐다).
