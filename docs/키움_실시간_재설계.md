# 키움 실시간(웹소켓) — 전수 확인과 재설계

2026-08-21. 근거는 `키움 REST API 문서 (1).xlsx` (344 시트).

## 먼저: 내가 틀렸던 것

**웹소켓 실시간시세 23종은 2026-08-10 에 받은 파일에 이미 다 있었다.** 나는 그 파일을
열어보지 않고 REST TR 만 뒤졌고, 그 상태에서 「키움이 안 준다」고 코드 주석까지 달았다.
거래원 시간대별을 「화면을 열 때마다 한 점씩 쌓는」 방식으로 만든 게 그 결과다 —
장이 끝난 뒤엔 누적값이 안 변하니 **같은 값이 여러 줄 찍히는 화면**이 됐다.

교훈은 하나다. **받은 자료를 먼저 다 읽고 나서 없다고 말할 것.**

## 확인 결과

### ① 실시간으로 받을 수 있다 (지금은 폴링으로 때우는 중)

| TR | 이름 | 지금 우리 방식 |
|---|---|---|
| `0B` | 주식체결 | `ka10003` 폴링 (체결강도) |
| `0D` | 주식호가잔량 | 호가 폴링 |
| `0F` | **주식당일거래원** | 화면 열 때 한 점씩 — **틀린 화면** |
| `0w` | **종목프로그램매매** | 폴링 |
| `0J` `0U` | 업종지수 · 업종등락 | 폴링 |
| `1h` | **VI발동/해제** | **아예 없음** |
| `0s` | 장시작시간 | 시간으로 추정 |
| `0g` | 주식종목정보 | 없음 (관리종목·VI 등 시장조치) |
| `0E` | 주식시간외호가 | 없음 |
| `0H` | 주식예상체결 | 없음 |

접속 규약 (모든 TR 공통):

```
wss://api.kiwoom.com:10000/api/dostk/websocket

등록  {"trnm":"REG","grp_no":"1","refresh":"1",
       "data":[{"item":["005930"],"type":["0w"]}]}
해지  {"trnm":"REMOVE", ...}
수신  {"trnm":"REAL","data":[{"type":"0w","item":"005930","values":{"20":"113442",...}}]}
```

`item` 은 거래소별 코드 (`KRX:039490`, `NXT:039490_NX`, `SOR:039490_AL`).
`values` 는 **FID 번호**가 키다.

`0w` FID: `20`체결시간 `10`현재가 `11`전일대비 `12`등락율 `13`누적거래량
`202`매도수량 `204`매도금액 `206`매수수량 `208`매수금액
`210`순매수수량 **`211`순매수수량증감** `212`순매수금액 **`213`순매수금액증감** `215`장운영구분

**「증감」이 따로 온다.** 우리가 차분을 계산할 필요가 없다.

### ② 내가 「막혔다」고 한 것 — 다시 판정

| 항목 | 판정 |
|---|---|
| `ka00190` 대량체결상위 | **막힌 게 아니었다.** 아래 참고 |
| 선물 수급 | **진짜 막혔다.** 문서 344 시트 전체에 선물·옵션 TR 이 **0건** |
| 증시주변자금(예탁금·신용잔고) | **진짜 막혔다.** 키움 문서에 언급 0건 → 공공데이터포털 그대로 |
| 고정 채널 동작 확인 | 그대로 (미니PC 에서 확인해야 함) |

#### `ka00190` — 내가 틀리게 불렀다

필수(Y)로 표시된 것 중 **빈 문자열로 보내야 하는 것들**이 있다. 문서의 요청 예시:

```json
{"mrkt_tp":"000","sort_tp":"1","case_pric_tp":"1",
 "trde_prica_tp":"", "stk_tp":"", "trde_qty_tp":"",
 "crd_tp":"0","pric_tp":"0","mac_tp":"0",
 "price_cnd_tp":"","price_cnd_min":"","price_cnd_max":"",
 "price_cnd_min_sign":"","price_cnd_max_sign":"",
 "mac_cnd_tp":"","mac_cnd_min":"","mac_cnd_max":"",
 "mac_cnd_min_sign":"","mac_cnd_max_sign":"",
 "trde_prica_cnd_tp":"","trde_prica_cnd_min":"","trde_prica_cnd_max":"",
 "trde_prica_cnd_min_sgin":"","trde_prica_cnd_max_sign":"",
 "trde_qty_cnd_tp":"","trde_qty_cnd_min":"","trde_qty_cnd_max":"",
 "trde_qty_cnd_min_sign":"","trde_qty_cnd_max_sign":"",

```

나는 필수 10개를 **전부 값으로 채웠고**, 조건 필드(`price_cnd_*` 등)는 아예 안 보냈다.
그래서 `return_code 0` 인데 결과가 0건이었다 — 필터가 전부 걸러낸 것이다.
(`trde_prica_cnd_min_sgin` 은 문서 오타 그대로 써야 한다)

## 재설계

### 원칙

**웹소켓은 서버가 문다. 화면은 서버가 쌓아 둔 것을 읽는다.**

화면이 직접 붙으면 창을 열 때만 쌓이고, 창이 여럿이면 연결도 여럿이 된다.
지금 거래원이 쓸모없어진 이유가 정확히 그것이다.

### 구조

```
미니PC 서버
  realtimeClient.ts   웹소켓 하나. 로그인·재연결·PING/PONG·구독 관리
  realtimeStore.ts    받은 값을 종목별·TR별로 하루치 쌓는다 (파일)
  ↑ REST 토큰을 공유한다 (키움은 앱키당 토큰 하나)

화면
  기존 폴링 그대로 두고, 저장된 시계열만 새 엔드포인트로 읽는다
```

### 순서

1. `realtimeClient.ts` — 접속·구독·재연결. 붙는 것만 확인
2. `0w` 하나로 끝까지 — 저장 → 엔드포인트 → 프로그램매매 칸에 시간대별 그래프
3. 되는 걸 보고 `0F`(거래원)로 같은 길
4. `1h`(VI) — 지금 없는 정보. 급등락 감지에 바로 쓰인다
5. 나머지는 필요할 때

### 조심할 것

- **구독 수 상한을 모른다.** 관심종목 전부를 한 번에 걸면 거절당할 수 있다. 적게 시작한다
- **장중에만 돈다.** 마감 뒤엔 조용한 게 정상이고, 그걸 「고장」으로 읽지 않게 화면에 적어야 한다
- **토큰이 하나뿐이다.** 웹소켓이 토큰을 새로 받으면 REST 쪽이 죽는다. 반드시 같은 토큰을 쓴다
- **재연결이 본체다.** 하루 종일 물고 있어야 하므로 끊김 처리가 기능의 절반이다
